設計原則（その原理をどう設計に落とすか）を示す。
実装方法ではなく、設計の**判断基準**である。

定義された「原理」を**設計判断の基準**へ具体化したものである。

設計時に迷った場合は、必ず本原則に立ち戻ること。

## APIは契約

APIは実装ではなく「契約」である。

- クライアントとの合意事項である
- 互換性を壊してはならない
- 変更は常にバージョン戦略とセットで行う

内部構造の変更は自由だが、外部契約の変更は慎重に行うこと。

公開済みAPIの予告なき変更は契約違反である。

---

## リソース指向

リソース試行APIで標準化を行うことを原則とする。

APIは「動作」ではなく「**リソース**」を中心に設計する。
APIは命令の集合ではなく、**状態を持つリソースへの操作**である。

操作はリソースに従属する。これにより、操作の乱立を防ぎ、構造を安定させる。

```
API = リソース × 許可された操作（API）
```

NG例:

```
POST /createUser
POST /deleteFile
```

---

## 単一責務

一つのAPIは、一つの明確な**目的のみ（責務のみ）**を持つ。

多目的なAPIは複雑性を内包する。
責務が曖昧なAPIは利用者の推測を困難にする。

APIは「できること」ではなく、「やるべきこと」を提供する。

---

## 一貫性・予測可能性

APIの一貫性は学習コストを下げるため、**同じ概念は、常に同じ表現**を使うこと。

- 命名規則（snake_case / camelCase を統一）
- 名称統一（number、num、no を統一）
- 日付形式（ISO 8601）
- ID形式（UUID、ULID、連番 など）
- エラーフォーマットの統一

---

## HTTPセマンティクスの尊重

| メソッド | 説明                            |
| -------- | ------------------------------- |
| POST     | リソース 新規作成（副作用禁止） |
| GET      | リソース 取得                   |
| PUT      | リソース 置き換え（全体更新）   |
| PATCH    | リソース 部分更新               |
| DELETE   | リソース 削除                   |

ステータスコードは、意味に従って返すこと。
ステータスコードを曖昧に使用してはならない。

---

## 最小驚愕の原則

APIは利用者を驚かせてはならない。

- GETで状態変更する
- PUTで一部更新しかしない
- DELETEでリソースを削除しない（204で作成成功）
- 400でシステムエラー

---

## エラーは制約の宣言

制約は隠してはいけない。
ステータスコード、エラーコードを用いてレスポンス形式で明示する。

エラーは、クライエントに何ができて、何ができないかの情報を提供する。
エラーは「操作の境界の設計」と「システムによるハンドリング」として提供する必要がある。

- 操作の境界の設計は、人間の読みものであるため、日本語でメッセージとする。
- システムによるハンドリングは、システムが扱いやすいように、コード値（ただし言葉）とする

---

## 冪等性

冪等性は時間に対する責任である。
冪等性とは、冪等性とは、同じリクエストを複数回繰り返しても、単一の効果が得られる（毎回同じレスポンス）こと。

非冪等なAPIは、**冪等性を保証**すること。
必要に応じて冪等設計を行う（Idempotency-Keyなど）。

| メソッド | 冪等性                     | 注意や補足                 |
| -------- | -------------------------- | -------------------------- |
| POST     | 非冪等                     | 新規作成                   |
| GET      | 冪等                       | 取得                       |
| PUT      | 基本的に冪等               | 全体更新 or 作成 or UPSERT |
| PATCH    | 基本的に冪等だが場合による | 部分更新                   |
| DELETE   | 冪等                       | 削除                       |

---

## 状態遷移の明示

APIによってリソース状態が更新されることを意識して設計する。

リソースは「 `存在しない` → `作成` → `更新` → `削除` 」などとライフサイクルを持つ。

リソース内に状態の遷移も意識して設計する。
一貫した状態遷移とする。

「 `DRAFT` → `PUBLISH` → `UNPUBLISH` 」

設計時に以下を明示すること

- 状態一覧
- 許可される遷移（`DRAFT` → `PUBLISH`）
- 禁止される遷移（`UNPUBLISH` → `DRAFT`）

---

## 並行処理や非同期処理

並行処理・非同期処理を崩さない設計でなければならない。

非同期処理は「隠蔽」してはならない。

- 非同期であることを明示する
- 処理中状態を表現する
- 完了確認手段を提供する（ポーリング、Webhookなど）

曖昧な成功レスポンスは禁止。

---

## バージョニング戦略の明確化

破壊的変更は必ずバージョンで分離する。

```
/api/v1/
/api/v2/
```

また、バージョン状態を持たせて段階的な移行とする。

「`未完成` → `現行` → `非推奨` → `削除`」

---

## 意味は言葉で表す

エラーコードや種別に連番や数値を使用してはいけない。文字で示すこと。
また、名称は重要な設計であり、言葉のニュアンスなどに気をつけてること。

NG:

```
gender=1
error=001
```

OK:

**エラーコード**

```
gender=MALE
error=EMAIL_INVALID_FORMAT
```

言葉は一貫した使用として同じ言葉を使用する。
APIごとに使用する言葉が異なってはならない。

`number` 、 `num` 、`no`

ドメインに沿った言葉を使用しなければならない。

---

## セキュリティ重視

APIは常に攻撃対象になり得る。

- 認証・認可を明示
- 入力値検証（バリデーション）
- ファイル検査
- レート制限
- 機密情報の非公開

---

## 負荷・性能

APIは低負荷時だけ正しく動けばよいものではない。
負荷増大するを前提に設計する。

- ページネーションを前提
- カーソル方式を優先
- 巨大なレスポンス設計をしない
- 重い処理は非同期化する
- タイムアウトを設計に含める

---

## 拡張性

APIは将来変更されることを前提とする。

- 追加フィールドは破壊的変更にしない
- 種別は列挙子で定義する
- 必須項目、任意項目は慎重に定義する
- レスポンス構造を安易にネストしすぎない

拡張性とは「将来の変更を破壊にしない設計」である。

## 観測可能性

APIは運用される前提で設計する。

- （必要に応じて）リクエストIDを持つ
- ログに追跡情報を含める
- メトリクスを収集可能にする
- エラー率を監視可能にする

---

## APIはUIの都合で歪めない

APIは特定画面のために存在しない。

先ず、更新系と参照系を分ける。
次に、参照系は、「業務としての参照」（ドメイン）と「画面描画のための参照」を分ける。

画面専用APIはドメインを破壊しないように分離して定義すること。
