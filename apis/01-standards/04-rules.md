## 強制度

本ガイドラインは MUST / SHOULD / MAY に基づく。

`MUST` : 必須。違反は不可
`SHOULD` : 原則必須。例外は設計レビュー承認が必要
`MAY` : 任意

## リソース指向設計

```
API = リソース × メソッド
```

- APIはリソースを中心に設計しなければならない（MUST）
- 動詞をパスに含めてはならない（例: /createUser は禁止）（MUST）
- リソースは複数形で定義する（/users）（MUST）
- 動作（コマンド）のようなリソース操作で表現できない場合のみ、POST + アクション形式を使用してよい（SHOULD）

| メソッド | 説明                          | 冪等性                 | ルール                                         |
| -------- | ----------------------------- | ---------------------- | ---------------------------------------------- |
| POST     | リソース 新規作成、アクション | 非冪等                 | 何でもPOSTにしないこと（MUST）                 |
| GET      | リソース 取得                 | 冪等                   | 作成や更新は禁止（MUST）                       |
| PUT      | リソース 置き換え（全更新）   | 基本的に冪等           | 更新or作成は可能だが原則、部分更新不可（MUST） |
| PATCH    | リソース 一部更新             | 基本冪等だが場合による | PUTを第一選択に考えること（SHOULD）            |
| DELETE   | リソース 削除                 | 冪等                   | 削除以外に使用しない（MUST）                   |

## 冪等性（べきとうせい）

> 冪等性とは、同一リクエストを複数回実行しても、リソースの最終状態が同一になること。

- GET, PUT, DELETE は冪等でなければならない（MUST）
- POST は非冪等とする（MUST）
- 非冪等APIは **Idempotency-Key** を必須とする（MUST）
- PATCH は原則冪等とする（インクリメント操作は禁止）（SHOULD）

[冪等性（Idempotency-Key）の詳細はこちら](/apis/standards/idempotency)

## 命名規則（MUST）

| 項目                         | 文字                                   | 例                   |
| ---------------------------- | -------------------------------------- | -------------------- |
| HTTPヘッダー                 | パスカルケバブケース（トレインケース） | Pascal-Kebab-Case    |
| URLパス                      | ケバブケース                           | kebab-case           |
| パスパラメーター             | ローワーキャメルケース                 | lowerCamelCase       |
| クエリパラメーター           | ローワーキャメルケース                 | lowerCamelCase       |
| JOSNボディ                   | ローワーキャメルケース                 | lowerCamelCase       |
| 定数、種別、エラーコードなど | スクリーミングスネークケース           | SCREAMING_SNAKE_CASE |

- フラグは原則使用しない（MUST）
- 種別やエラーコードに数字、アルファベット1文字は禁止（MUST）
- 単語は省略しないこと（Idなどの一般的に省略される文字は許可する）。（MUST）
- 単語は統一すること（Number か Num、 Dcc か DCC、Type か Kind）（MUST）
- 日付・時刻の値はISO 8601形式とする（例: 2024-05-20T10:00:00Z）（SHOULD）

## メソッド

それぞれのメソッドを適切に使い分けること（MUST）

例

```
POST   /users
GET    /users/{userId}
PUT    /users/{userId}
PATCH  /users/{userId}
DELETE /users/{userId}
```

## パス

基本的なパスの構成は以下とする。（MUST）

「 `種別`/`バージョン`/`リソース`/`{識別子}`:`アクション` 」
（`/api/v1/books/bookId:publish`）

- パスは最大5階層までとする（先頭を除いた`/`の数）（SHOULD）
- 1つのAPIに複数のアクションを含めてはならない（MUST）
- アクション形式は最終手段とする（MUST）

### OKな例

| メソッド | パス                                    | 説明                                                                 |
| -------- | --------------------------------------- | -------------------------------------------------------------------- |
| GET      | `/api/v1/books`                         | 一覧取得                                                             |
| GET      | `/api/v1/books/{bookId}`                | 特定のリソース取得                                                   |
| GET      | `/api/v1/books/{bookId}/author`         | 特定のリソースの中の特定のプロパティ取得（リソースが大きい場合のみ） |
| GET      | `/api/v1/books/{bookId}/pages/{pageId}` | 階層構造などになっている特定のリソース取得                           |
| POST     | `/api/v1/books`                         | 新規作成                                                             |
| POST     | `/api/v1/books/{bookId}/pages`          | 特定のリソース内に新規作成                                           |
| POST     | `/api/v1/books/{bookId}:publish`        | アクション実行                                                       |
| POST     | `/api/v1/books/{bookId}/author:reset`   | 特定のプロパティに対するアクション                                   |
| PUT      | `/api/v1/books/{bookId}`                | リソース置き換え                                                     |
| PUT      | `/api/v1/books/{bookId}/pages/{pageId}` | 特定のリソース置き換え                                               |
| PATCH    | `/api/v1/books/{bookId}`                | 一部更新                                                             |
| PATCH    | `/api/v1/books/{bookId}/author`         | 特定のプロパティを一部更新                                           |
| DELETE   | `/api/v1/books/{bookId}`                | リソース削除                                                         |
| DELETE   | `/api/v1/books/{bookId}/pages/{pageId}` | 特定のリソース削除                                                   |

### NGな例

| メソッド | パス                                                         | 理由                 |
| -------- | ------------------------------------------------------------ | -------------------- |
| POST     | `/api/v1/createBooks`                                        | 動詞（操作）で定義   |
| POST     | `/api/v1/books/{bookId}:publish:reset`                       | アクションを複数使用 |
| GET      | `/api/v1/{bookId}`                                           | リソースのない識別子 |
| GET      | `/api/v1/books/{bookId}/sections/{sectionId}/pages/{pageId}` | パスが多い           |
| DELETE   | `/api/v1/book`                                               | リソースが単数系     |

### 種別

- 1単語で示す（MUST）
- apiかhtmlを返すか示す（SHOULD）
- 特定の権限を示す(MAY)
- プロキシーでのルーティングを意識する（SHOULD）

例

- `/api`
- `/web`
- `/admin`

### バージョン

- 後方互換性がない変更時にバージョンを上げること（MUST）
- 互換性のある変更（バグの修正）は同バージョンのままとする（MUST）

**v1からバージョンを上げる際の流れ**

1. v1とv2を並行して使用する可能とする
2. v1を非推奨とする
3. 徐々にv2に移行を促す
4. v1を削除する

**バージョン状態（MUST）**

| 状態                  | 説明                               | 変更ポリシー   |
| --------------------- | ---------------------------------- | -------------- |
| Preview（プレビュー） | 不安定で未完成                     | 全ての変更許可 |
| Current（現行）       | 安定して機能を提供                 | 必須のみ変更   |
| Deprecated（非推奨）  | 削除予定。現行の前バージョン       | 必須のみ変更   |
| Deleted（削除）       | 削除された、あるいは利用不可な状態 | -              |

### リソース

> リソースとはAPIを通じて操作や取得ができる「**情報のまとまり（データや機能）**」を指す抽象的な概念」である。

- リソースは複数形で示す（MUST）
- リソースは複数指定可能（SHOULD）
- 動詞はリソースではない（MUST）

### 識別子（パスパラメーター）

> **リソースを特定する**ために使用される値。

識別の条件は以下の通り

- ユニークであること（MUST）
- 変更されないこと（SHOULD）
- セキュアな場合は予測困難であること（ランダム性）（MUST）
- 波括弧で示す（`{userId}`など）（MUST）
- 識別子を単にIDとするのは禁止（userIdやBookIdなど自然な言葉を使用）。（MUST）
- `ID`の`D`は小文字とする（NG: `userID` , OK: `userId`）。（MUST）

識別子は、リソースの全件取得や新規作成などで必要ない場合は不要。（MUST）

### アクション

- リソース操作で表現できない、コマンドのような動作を表す場合に使用する（MUST）
- POSTのみ（MUST）
- 特に必要ない場合にアクションを使用してはならない（MUST）

### クエリパラメータ

> パスパラメーターはリソースを特定するが、クエリは**特定の条件**を加えるために利用する。

代表的な例

- `offset&limit（cursorとnextCursorなど）`でページネーション
- 価格順や新着順などのソート条件
- 何月の情報などの絞り込み条件

## ヘッダー

### Content-Type

基本的に、`application/json`を使用すること。

代表的な例

- JSONの場合、`application/json`
- formの場合、`application/x-www-form-urlencoded`
- HTMLの場合、`text/html`
- 画像の場合、`image/jpeg`、`image/png` など

その他、適切なものを選んで使用すること

※ GETリクエストボディには通常Content-Typeは不要

### Authorization

認証情報を含める。（MUST）
認証に必要なトークンなど（主にJWT、たまにBasic）。

※ JWTにはユーザーを識別する情報が含まれる。

- 認証が不要なAPIは明示すること（MUST）
- 認証が必要なAPIはAuthorizationヘッダを必須とする（MUST）

### Idempotency-Key（冪等性キー）

非冪等なAPIを冪等性を保証するために使用する（MUST）。

GETなどの冪等APIには不要だが、POSTなど非冪等APIでは必須。（MUST）

[冪等性キー](/apis/standards/idempotency)を参照すること。

## データ

### 型

- 値に応じて適切な型を用いること（MUST）
- int32とint64を意識すること（MUST）
  - 年齢や個数はint32
  - 金額など値が大きくなる場合はint64
- 数値でもカード番号や取引番号など数字でも文字列を使用する方が望ましい値は文字列とする（MUST）
- booleanは禁止しないが、本当にbooleanが適切かは検討すること（わかりずらい、組み合わせが必要になり複雑になりやすい）（SHOULD）

### 構造化

- 意味のあるまとまりで定義して構造化する（SHOULD）
- しかし、ネストを深くしすぎないこと（できる限りフラットにする）（SHOULD）
- ネストは最大2階層（親子）まで（SHOULD）、最大でも3層まで（MUST）

例として示すが、状況によりまとめた方が良い場合とネストせずに、フラットとした方が望ましい場合がある。
まず、フラットにできないかを考え、フラットな構造が適切ではないと判断される場合においてのみ、まとめること。

NGな例

```json
{
  "bookId": "xxx",
  "bookName": "xxx",
  // 著者として意味を持つためまとめる
  "authorId": "xxx",
  "authorName": "xxx",
  "authorCode": "xxx",
  "authorRole": "xxx"
}
```

OKな例

```json
{
  "bookId": "xxx",
  "bookName": "xxx",
  "author": {
    "authorId": "xxx",
    "authorName": "xxx",
    "authorCode": "xxx",
    "authorRole": "xxx"
  }
}
```

### 列挙型

定数、種別、ステータスは、**列挙型**を使用すること。（MUST）

:::warning
定数、種別、ステータスなどを表す場合は、数字（1、2、3）、記号（あいう、acb、!@など）の使用を原則禁止する（やむを得ない事情がない限り可）。

意味のある文字を使用することべきだ。

フラグ（数字や記号）が何を意味しているのか読み取りずらく、利用者に負荷を強いる。
:::

### 日付・時刻

- 原則、ISO 8601 形式とする（SHOULD）
- JSTを第一選択とする（MUST）

| 形式・規則                | 具体的な例                |                   |
| ------------------------- | ------------------------- | ----------------- |
| YYYY-MM-DD                | 2024-05-20                | 日付のみ          |
| hh:mm:ss                  | 10:00:00                  | 時刻のみ          |
| YYYY-MM-DDThh:mm:ssZ      | 2024-05-20T10:00:00Z      | 日付と時刻（UTC） |
| YYYY-MM-DDThh:mm:ss+09:00 | 2024-05-20T19:00:00+09:00 | 日付と時刻（JST） |

- 単にdateではなく、意味のある言葉を使用すること（MUST）
  - 過去のイベント（作成日など）: createdAt, updatedAt, publishedAt
  - 未来の予定（期限など）: expiredAt, scheduledAt
  - 論理的な日付（誕生日など）: birthday, startDate

### 未設定値の扱い

リクエストボディで任意項目を設定しない場合、
レスポンスボディで値を返さない場合は空（""）やゼロやnullではなく**未設定**とする（MUST）。

- nullを未設定の代替として使用してはならない（MUST）
- 空文字を未設定の代替として使用してはならない（MUST）

**name設定ありの場合**

```json
{
  "userId": "abc",
  "name": "たろう"
}
```

**name設定なしの場合**

```json
{
  "userId": "abc"
  // nameを未設定とする
}
```

## リソース作成時レスポンス

GETの目的をPOSTに持たせたくなることがあるが、必要以上にPOSTでレスポンス返して、GETの仕事を奪ってはいけない（MAY）。

あくまで原則ではあるが、識別子のみを返すなど最小限にすること。

### リスト

結果の総数を返したくなることがあるが、総数の返却は原則NGである。（SHOULD）

将来、予想よりも件数が増えると頭痛の種になる。リストの数と総数が異なるバグになるだけで、
数えたいのであれば利用者（クライエント）に数えてもらうべき。（SHOULD）

もしどうしても総数が必要な場合は、リストの件数と総数が一致することをAPIの処理の中でチェックすること。（MUST）

### リストのソート

ソートするべきケースは多いが、
「どの項目で（キー）」、「どの向きで（昇順、降順）」、「どの優先度で（キーが複数）」、ソートしているか明確にすること。（MUST）

件数が少なければ特に問題はないが、件数が多い場合には気をつけること（性能上の問題がなければソート実施はOK）。（MUST）

### リストのフィルタリング

クエリパラメーターに従って、フィルタリングを行い、必要なリソースのみを返す。（MUST）
ただし、原則的に、単純な条件のみとし、ANDやORで複雑な条件でフィルタリングするのは望ましくない。（SHOULD）

## リクエストボディ

- リソースを特定する場合はボティではなく、パスパラメーターを使用すること（MUST）
- GETやDELETEメソッドでは使用しない（MUST）
- 基本的にJSON形式とする（Content-Typeに合わせて適切な形式とする）（SHOULD）

例

```json
{
  "email": "user@example.com",
  "age": 25
}
```

## レスポンス

## HTTP ステータス

- 適切なステータスコードを選択すること（MUST）
- 何でも正常は200、何でも異常は400、これはNG。適切なエラーコードを使用する（MUST）
- 忘れがちな200で返しがちなステータスコード
  - POST `202 Accepted`
  - DELETE `204 No Content`
- `204 No Content` はレスポンスボディを含めてはならない（MUST）
- `401 Unauthorized`と`403 Forbidden`は混同しがちなため注意（MUST）
- `404 Not Found`を適切に使用すること（MUST）
  - 取得するリソースがない
  - 更新するリソースがない
  - 元のトランザクションが見つからない（決済の取消時に支払いレコードがない など）

| ステータスコード | タイトル               | 説明                                                                                                                                            |
| ---------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 200              | OK                     | 成功レスポンス。ただし、201や204などに該当しない場合                                                                                            |
| 201              | Created                | リソースが作成された場合に使用                                                                                                                  |
| 202              | Accepted               | 成功したが後続に実行する処理がある場合などに利用。主にバッチAPIで一旦レスポンスを返し（202）、その後、照会系APIをポーリングしてもらう場合など。 |
| 204              | No Content             | リソースのDELETEやPUTに成功したが特に返すものがない場合                                                                                         |
| 400              | Bad Request            | クライエントエラー。クライエントが原因でサーバーがリクエストを処理しなかった                                                                    |
| 401              | Unauthorized           | 有効な認証情報がない（認証失敗）                                                                                                                |
| 403              | Forbidden              | 認証はできていてもアクセスが禁止されている（認可失敗）アクセス権がないなど。                                                                    |
| 404              | Not Found              | 対象のリソースが存在しない場合（削除・更新するリソースがない、取消対象がない場合など）                                                          |
| 405              | Method Not Allowed     | 存在しないメソッドのリクエスト。APIに「POST」は存在するが、「GET」は存在しないのにGETを指定など。                                               |
| 409              | Conflict               | 現在のサーバー状態と競合した場合。同一リソースの処理中や階層構造のあるリソースで指定したリソースの親リソースが処理中など                        |
| 410              | Gone                   | 元々は存在していたが、現在は利用できなくなっているリソースにアクセスしている場合                                                                |
| 411              | Length Required        | Content-Lengthヘッダが必要だが指定されていない場合た                                                                                            |
| 415              | Unsupported Media Type | サポート外のメディアタイプを受信。JSON形式のはずがXMLを受信した場合                                                                             |
| 422              | Unprocessable Content  | コンテンツは正しいが、サーバーが処理できなかった場合。冪等性キーの使いまわしているなど。                                                        |
| 423              | Locked                 | 対象のリソースがロックされている場合。ログインでパスワードを何度も間違えてロックされた場合など                                                  |
| 429              | Too Many Requests      | 一定時間に一定以上のリクエストを受け付けた場合                                                                                                  |
| 500              | Internal Server Error  | サーバーで予期せぬエラーが発生した場合（システムエラー）                                                                                        |
| 502              | Bad Gateway            | ゲートウェイやプロキシーで不正なリクエストを受け取った場合                                                                                      |
| 503              | Service Unavailable    | サーバーメンテナンス中やサーバーが正常に動作していない場合                                                                                      |
| 504              | Gateway Timeout        | タイムアウトが発生した場合にゲートウェイやプロキシーなど                                                                                        |

### リソースがない場合

200を返すことも可能だが、削除するリソースがない場合は、`404 Not Found`を返す方針とする。

## エラーレスポンス

> 「エラーコードは堅牢・メッセージは説明的」 という理想形

| 値               | 意味                                                         |
| ---------------- | ------------------------------------------------------------ |
| タイプ（例外）   | 発生箇所を示す。大分類。アプリによっては不要。               |
| エラーコード     | クライエントのハンドリング用の値（プログラムが使用する前提） |
| エラーメッセージ | 原因説明用の値（原因調査などを目的）                         |
| 詳細情報         | 識別子を返す必要があるなど、どうしても必要な場合のみ使用     |

※ 詳細情報は使用しないこと（本当にどうしてもやむを得ない場合に限り）
※ 詳細情報を返す代わりにAPIのリクエストで識別子を受け取ることで、リソースを特定することができないか？など検討すること

```json
{
  "type": "string",
  "errorCode": "string",
  "errorMessage": "string",
  // 任意（基本的に使用しない。使用しないことが望ましい）
  "details": [
    {
      "field": "email",
      "value": "sample@mail.com"
    }
  ]
}
```

### タイプ（例外）の大分類

- タイプは必須ではない。高セキュアなアプリケーションではむしろ実装しない方が望ましい場合もある。

- プレゼンテーション例外
- ユースケース例外
- ドメイン例外
- インフラストラクチャー例外
- その他例外

セキュリティ上の懸念がある場合は隠蔽すること（MUST）

### エラーコード

責務は、クライエント（フロント）が「ハンドリング」を提供する。（MUST）
エラーコードは「`対象` と `原因`」とする。（MUST）

粒度は、システムが**ハンドリングする**という目的を軸に決めること。（MUST）

- enum として固定（UNAUTHENTICATEDなど）
- 後から意味を変えない
- 廃止はしても再利用しない
- ログの都合なエラーコードは使用しない
- DB名、API名は出してはいけない

#### 対象

- フィールド
- リソース
- 集約

#### 原因

- UNAUTHENTICATED
- EXPIRED
- PERMISSION_DENIED
- NOT_FOUND
- ALREADY_EXISTS
- CONFLICT
- TIMEOUT
- UNAVAILABLE
- INTERNAL_ERROR
- MISSING......必須フィールド未設定

#### 具体例

OKな例

- EMAIL_INVALID_FORMAT......フォーマット不正
- AMOUNT_MAX......最大値超過
- AMOUNT_MIN......最小値未満
- PASSWORD_TOO_LONG......最大桁数超過
- PASSWORD_TOO_SHORT......最小桁数未満
- PASSWORD_INVALID......値が不正
- AUTH_TOKEN_EXPIRED......有効期限切れ

NGな例

- INVALID......短すぎて不正以外何もわからない
- PASSWORD_MIN_LENGTH_8......細かすぎ
- VALIDATION_ERROR......どの値か不明、原因も不明瞭
- SERVICE_UNAVAILABLE......一時情報を含める（valkeyが落ちているなど）
- INVALID_001......数字を含めるのはNG

#### プレゼンテーション系

クライエントとの入出力に関するエラー

- XX_MISSING......項目の欠落
- XX_INVALID......形式や値が正しくない
- UNAUTHENTICATED......認証していない
- PERMISSION_DENIED......権限がない

#### ユースケース系

ドメインをまたぐルール、リポジトリから取得した値との不整合

- USER_ALREADY_EXISTS.....すでに存在している
- USER_NOT_FOUND......不存在
- CONTENT_DELETED......ステータス不正
- USER_DISABLED......ステータス不正
- ACCOUNT_LOCKED......ステータス不正
- OPERATION_NOT_ALLOWED......状態・業務ルール的に不可

#### ドメイン系

業務用語を使用したエラーコードとする

- USER_STATUS_INVALID......ステータス不正
- ORDER_EXPIRED......請求の有効期限切れ
- SUBSCRIPTION_EXPIRED......サブスクリプションの有効期限が切れ

#### インフラストラクチャー

細かい粒度で出すのではなく、大まかな分類でざっくりと

- SERVICE_UNAVAILABLE......一時的にリクエストを処理できない
- INTERNAL_ERROR......内部エラー
- TIMEOUT......タイムアウト

#### その他系

- INTERNAL_ERROR......サーバーエラー

### エラーメッセージ

責務は「人が原因を理解するための説明」を日本語で示す。（MUST）

表示用の文字列として使用してはいけない。（MUST）

「**何が** / **どの状態で** / **なぜ問題なのか**」を記載すること（MUST）

- 【対象】が【どういう状態】のため【何ができない／不正である】
- 【対象】が【制約】を満たしていない

#### プレゼンテーション系

- 認証情報が存在しない、または有効ではありません
- 認証トークンの有効期限が切れています
- この操作を実行する権限がありません
- 許可されているリクエスト回数の上限を超えています

#### ユースケース系

- 指定されたユーザーが存在しません
- 同一条件のユーザーがすでに存在します
- 対象のコンテンツはすでに削除されています
- 現在の状態ではこの操作を実行できません
- 現在の状態と要求された操作が矛盾しています

#### ドメイン系

- メールアドレスの形式が不正です
- パスワードが設定されていません
- パスワードの文字数が許可された最大値を超えています
- パスワードの文字数が許可された最小値を下回っています
- 注文の有効期限が切れています
- 契約の有効期間が終了しています
- 指定された方法は利用できません

#### インフラストラクチャー系

- 現在サービスを利用できない状態です
- 処理が規定時間内に完了しませんでした
- サーバー内部で予期しない問題が発生しました

#### その他

NGな例

- 具体的な値あり......「パスワードは8文字以上で入力してください」
- 対象なし......「不正です」
- API名が含まれる......「決済APIにおいて、取引上限金額を超過しています」
- 原因が不明......「失敗しました」
