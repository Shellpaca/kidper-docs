# Front-Matter

このページは、Docusaurus における フロントマターの共通ルールと運用方針を定義するためのものである。

フロントマターは単なるメタ情報ではなく、以下の目的を持つ。

- ドキュメントの 性質・鮮度・責任範囲 を明確にする
- 読者が「読むべきか」「今も有効か」を即座に判断できるようにする
- ドキュメントが増えた際に、一覧化・検索・自動チェックを可能にする
- 「書いたまま放置される資料」を減らす

本ルールは、**設計・実装・運用・セキュリティ・ドキュメント整備**といった異なる役割の人が同じリポジトリを見る前提で設計されている。

---

## テンプレート

```md
---
title:
description:
# draft: false      # true=未公開, false=公開
# sidebar_label:
# unlisted: false    #true=サイドバー非表示、false=表示
doc-kind: doc
  - usecase
  - api
  - domain
  - doc
  - operation
  - security
  - test
maintenance:
  - active # メンテナンス対象 現在進行中、または頻繁にアクセス・編集される
  - frozen # メンテナンスされない。変更は加えられない状態（過去の記録）
  - archived # 消極的なメンテナンスを行う。アーカイブ（古い可能性あり）
audience:
  - design # 設計判断をする人
  - implementation # 実装する人
  - verification # 正しさを検証する人
  - operation # 運用・障害対応する人
  - security # セキュリティ責任者
  - documentation # ドキュメント整備者
review-cycle: none
  - every-release # リリースごと
  - quarterly # 四半期ごと
  - none なし
tags:
  - upload
  - content
  - active
  - readme
related:
  - adr/ADR-0003
  - apis/content-upload
future:
  - チャンクアップロード統合
  - 非同期完了通知
---
```

## doc-kind

ページの**種別（ドキュメントの性格）**を表す。
「このページは 何について 書かれているか」を示す最も重要な分類。

| 値        | 説明         | 主な内容                                    |
| --------- | ------------ | ------------------------------------------- |
| usecase   | ユースケース | 利用シナリオ、業務フロー、ユーザー視点      |
| api       | API          | エンドポイント、リクエスト/レスポンス、制約 |
| domain    | ドメイン     | 用語、モデル、責務、業務ルール              |
| doc       | ドキュメント | ルール、方針、README、説明資料              |
| operation | 運用         | 手順、障害対応、監視、デプロイ              |
| security  | セキュリティ | 脅威、対策、ポリシー、制約                  |
| test      | 試験・品質   | テスト方針、観点、品質保証                  |

### 意図

- ドキュメントの役割を明確にする
- 同じ粒度・同じ期待値で読めるページを揃える
- audience や review-cycle の判断材料にする

## maintenance

そのドキュメントが `現在もメンテナンス対象かどうか` を示す。

| 値       | 説明       | メンテナンス | 期待される状態                                 |
| -------- | ---------- | ------------ | ---------------------------------------------- |
| active   | アクティブ | 対象         | 仕様変更時に必ず更新される                     |
| archived | アーカイブ | どちらとも   | 現行仕様ではないが参照される。古い可能せに留意 |
| frozen   | 凍結       | 対象外       | 過去の決定・履歴。原則変更しない               |

#### 意図

- 「この情報は今も正しいか？」を即判断できるようにする
- 更新責任があるページと、履歴として残すページを区別する
- 古い仕様に引きずられた実装・運用ミスを防ぐ

## audience

このドキュメントの**主な読者**を表す。
複数指定可。
「誰のための情報か」を明示することで、記載粒度・前提知識・表現レベルを揃える目的がある。

| 値             | 想定読者           | 主な関心事                 |
| -------------- | ------------------ | -------------------------- |
| design         | 設計判断を行う人   | 構造・責務・トレードオフ   |
| implementation | 実装担当者         | 実装方法・API仕様・制約    |
| verification   | テスト・検証担当   | 正しさ・境界条件・検証観点 |
| operation      | 運用・障害対応担当 | 監視・復旧・運用手順       |
| security       | セキュリティ責任者 | 脅威・対策・権限           |
| documentation  | ドキュメント整備者 | 構成・一貫性・表現         |

### ルール

- 迷ったら「誰がこのページを最初に読むか」で決める
- `audience` が `design` の場合、背景・理由・代替案を省略しない
- `implementation` のみの場合、設計判断の詳細は関連ドキュメントに委譲してよい

---

## review-cycle

この文書を**見直す責任が発生するタイミング**を示す。
「いつ更新されるべきか」を機械的に判断できるようにする目的。

| 値            | 意味                     |
| ------------- | ------------------------ |
| every-release | リリースごとに必ず見直す |
| quarterly     | 四半期ごとに棚卸しする   |
| none          | 定期レビュー対象外       |

### 指針

- API仕様・運用手順 → every-release
- 設計思想・ADR → none または quarterly
- 古いが参照される資料 → none + maintenance: archived

## tags

ページ内容を`横断的に分類するためのタグ。
`横断的な検索性・一覧性`を高める目的で使用する。

以下は例

1. 機能・関心領域

upload
auth
notification
content

2. 状態・性質

active
deprecated
experimental

3. ドキュメントの役割

readme
overview
guideline

ルール

- 独自に決めてよい
- 英語・小文字・スネークケース
- 3〜5個までを目安
- 技術要素・機能・状態を表す
- 意味が重複するタグは避ける

---

## related

関連ドキュメントへの参照。
**「一緒に読むべきページ」**を明示する。

### 用途

- ADR へのリンク
- 詳細仕様ページへの導線
- 前提となる設計・制約の明示

### ルール

- 相対パスで記載する
- 強い依存があるもののみ記載する
- 存在しない場合は `none` を明示してもよい

---

## future

### 目的

- 未対応・TODO を埋もれさせない
- 「なぜ今は無いのか」を説明する
- 将来変更時の影響範囲を把握しやすくする

### ルール

- 実装確定でなくても記載してよい
- 完了したら削除 or 別ドキュメントへ移動する
- 長期放置される場合は `maintenance` を見直す
