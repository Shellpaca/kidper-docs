## 目的

Architecture Decision Record（ADR）の記録であり、
設計上の「判断」と「理由」を将来に残す。

> ADR = ソフトウェアやシステムの設計における意思決定（**なぜこの設計判断をしたのか**）を残すための短い記録

---

## 記載内容

- **Status**: ADRの状態を示す
- **Context**: なぜ検討が必要だったか
- **Decision**: 採用した判断
- **Consequences**: その結果生じる影響・制約

---

## 記載しないこと

- 経緯以外の仕様書や作業報告書に該当する事柄
- 単なる作業ログや進捗報告
- 個人の感情や責任の押し付け

---

## 位置づけ

- 過去の記録（仕様書ではない）

---

## 特徴やルール

- 1ファイル = 1判断
- 短く、背景と結論に集中
- 不変（Immutable）の原則に従う。Accepted になった ADR は、内容を直接書き換えない。
- 状況が変わった場合は、新しい ADR を作成し、古い方を Superseded に更新してリンクを張る。
- ファイル名は、「ADR-\*\*（数字）-xxxx（タイトル）.md」

---

## 記載内容詳細

### テンプレート

```
# ADR [番号]: [簡潔なタイトル]

## ステータス

[Proposed | Accepted | Rejected | Superseded by ADR-XXXX]

## コンテキスト (背景)

- どのような課題や制約（技術、予算、納期など）があるか？
- なぜ今、この決定が必要なのか？

## 検討した選択肢 (Options)

- 案A: [名称] (メリット/デメリット)
- 案B: [名称] (メリット/デメリット)
- 案C: [名称] (メリット/デメリット)

## 決定 (Decision)

- どの案を採用するか？
- 採用に至った決定的な理由は何か？

## 結果・影響 (Consequences)

- この決定によって何が良くなるか？
- 新たに生じるリスクやトレードオフ、作業内容は何か？

## 記録

- 起案者: [名前]
- 承認者: [名前/チーム名]
- 日付: YYYY-MM-DD
```

### Status

| ステータス | 説明       | 意味                                                                       |
| ---------- | ---------- | -------------------------------------------------------------------------- |
| Proposed   | 提案中     | 解決策を提示し、チーム内でのレビューや議論を待っている状態                 |
| Accepted   | 承認済み   | 議論が終わり、チームがその設計方針に従うことに合意した状態                 |
| Rejected   | 却下       | 提案されたが、何らかの理由で採用されなかった状態（なぜダメだったかを記録） |
| Superseded | 置き換え済 | 過去の決定が、新しい決定（別の ADR）によって上書きされた状態。             |
| Deprecated | 廃止       | そのコンポーネント自体が削除されるなど、決定がもはや不要になった状態       |
